# osu! Replay Analyzer: SPEC

Stable facts and rules. Claude: do not edit this file unless the user asks.
Living details (modules, schema, decisions) go in ARCHITECTURE.md.
The current task is named in NOTES.md and defined in milestones/.

## 1. Goal
A fast, fully offline, native desktop app that analyzes ALL of a user's
osu!lazer replays, not just API top plays. It re-simulates hit detection from
replay data and caches every hit, so heatmaps, timing graphs, skill profiles
and training suggestions are computed over thousands of plays.

## 2. Platform and stack
- Linux first (Arch). Windows and macOS later as separate builds.
- Rust, eframe/egui (native GUI). No browser, no web server, no network.
- Crates: rosu-map (.osu parsing), rosu-pp (difficulty and PP), rusqlite
  (SQLite), rayon (parallel scanning). Pin exact versions in Cargo.toml.
- Prefer existing crates over writing parsers.

## 3. Hard rules
- Must treat the lazer data folder as READ-ONLY. Never write to it.
- Must open any lazer database file from a copy, never in place.
- Must NOT read client.realm. Identify files by content instead.
- Must NOT require the network.
- Must store an analyzer_version in the cache; changing any algorithm bumps it
  and triggers recompute.
- Must recompute PP with ONE pinned rosu-pp version. Never mix with stored PP.
- Must show sample counts wherever a number comes from binned data.
- Must report units. Keep cursor data in osu!px unless the user enters a
  tablet area in mm.

## 4. Scope v1
- osu!standard only.
- Circles and slider heads only. Slider ticks, ends and spinners come later.
- Exclude replays that are not the user's own (watched or imported).
- Exclude cheat mods: Relax, Autopilot, Auto, Cinema.
- Candidate maps for recommendations come from the local library only.

## 5. Data sources (lazer)
- Normal install: ~/.local/share/osu/
- Flatpak install: ~/.var/app/sh.ppy.osu/data/osu/
- Both paths are from memory: verify against the real machine.
- Inside: client.realm (ignored) and files/, where every file is stored under
  its content hash.
- Replays (.osr-style) contain a header with the beatmap MD5. Beatmaps (.osu)
  start with a known text line. Match replay to beatmap by MD5.
- The replay layout used by lazer is NOT verified. M01 must inspect real files
  before writing a parser.
- Config: a manual folder override and the player's name (to detect own
  replays) live in a config file under ~/.config/osu-analyzer/.

## 6. Glossary
- offset_ms: hit time minus object time. Negative = early, positive = late.
- UR (unstable rate): 10 x standard deviation of offset_ms.
- judgement: 300, 100, 50 or miss.
- key: which input pressed the hit (K1, K2, M1, M2).
- object density: number of objects per playfield bin, summed over maps.
- clicks per object: click density divided by object density.
- directional bias: mean cursor position relative to the circle centre, taken
  at the moment the offset is 0 ms. Red channel = x (more red = more
  rightward). Blue channel = y (more blue = more upward).
- Potential (radar): what maps the player can clear, from difficulty attributes.
- Demonstrated (radar): what replays show, e.g. accuracy and consistency
  under load.
- recent form: plays weighted toward the last weeks. all-time: unweighted.

## 7. Global behaviour (every page)
- A persistent filter bar: mods, date range, star range, best-only vs all
  plays, include fails.
- Every number is clickable and opens the plays or maps behind it.
- Every page offers recent-form and all-time weighting where it makes sense.

## 8. Pages and requirements

### Overview
- Total plays, hours played, PP per play over time, plays per month,
  accuracy over time, mod usage.

### Analysis: heatmaps
- Heatmaps: accuracy% (median at each point), click density, mean offset
  error, unstable rate, directional bias.
- Click density must be divided by object density (clicks per object).
- Controls: toggles for 300 / 100 / 50 / miss, a smoothing slider, a
  minimum-sample slider. Low-sample bins fade. Hover shows sample count.
- Smoothing must be instant: bin at 128x96 storing sum, sum-of-squares and
  count per bin, then blur at display time.
- Hard Rock is un-flipped so all maps use true playfield coordinates.

### Analysis: keys
- Overlaid hit-timing histograms per key.
- Key stats table: hits, UR, mean offset ms, std ms.
- Stamina curve: timing error vs elapsed time, normalized by local note
  density (compare only sections of similar density).

### Playstyle
- Most played styles and top styles by PP (alternate, stream, burst, jump,
  tech).
- Played style vs mapped style (detected from the key actually pressed).
- Accuracy grid by spacing x time gap.
- Bias by movement direction and by BPM.
- Skill radar, 8 axes maximum, each with a written formula. Two overlaid
  shapes: Potential and Demonstrated.

### Training
- Maps similar to what the user plays now (recency-weighted) that train the
  weakest radar axes.
- Maps similar to what the user plays now that award the most PP.
- A would-be PP column for hypothetical accuracy. Flag underplayed maps
  where predicted performance exceeds the player's best.

### Tablet
- Real used area (99.5th percentile bounding box), edge usage, rest jitter,
  peak cursor speed. Plain-English tips (e.g. area could be thinned or
  shortened) once the user enters their tablet size.

### Data
- Hours played, most-retried maps, key usage split, per-mod breakdowns.

### Later pages
- Sessions (group plays by time gaps; warm-up, fatigue, tilt, time of day).
- Retry analysis (attempts to pass, improvement curve).
- Single-play detail (hit error bar, cursor trail, click timeline).
- Compare (two time ranges or two plays).
- Progress (radar shape month by month).
